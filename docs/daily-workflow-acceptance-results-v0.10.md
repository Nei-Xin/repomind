## Method

The fixture began as a small dependency-free inventory repository with a
documented reservation contract. RepoMind initialized the repository and
generated two deterministic bootstrap candidates from the README and Git
history. Applying without `--yes` was rejected. The acceptance then applied
only the README candidate and left the lower-confidence Git-history candidate
unselected.

Task 1 asked OpenCode to implement `reserveInventory` and focused tests. After
the Host-managed session committed, external checks confirmed the contract and
the fixture change was committed. Task 2 then asked OpenCode to add atomic
`reserveBatch` behavior by reusing `reserveInventory`. Its run report records
retrieval of the solution memory generated by task 1, establishing actual
cross-task memory reuse rather than only successful storage.

Finally, a third `repomind run` used a one-millisecond timeout. The process was
terminated with `SIGTERM`, returned a nonzero CLI exit, abandoned both session
and Host-run state, and made no repository change. Public and external hidden
checks were rerun afterward.

## Limits

- This is a longitudinal product-path acceptance, not a no-memory or
  full-history comparison and not evidence of a general performance gain.
- It covers one small JavaScript repository, one model alias, one OpenCode
  version, two successful tasks, and one forced timeout.
- The initial seed became uncertain after the README changed. The run proves
  stale status is surfaced, but does not evaluate a human revalidation flow.
- The one-millisecond timeout validates early process cleanup; it does not
  exercise interruption after the Agent has edited files.
