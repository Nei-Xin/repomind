## 方法

该套件包含四个任务，每个任务在两个实验组中各运行三次：共 12 组配对比较，
24 次 Agent 运行。每组都从同一任务 commit 的全新克隆开始。每次重复实验会交替
A/B 执行顺序。隐藏检查保留在工作仓库之外，每个 RepoMind 组使用隔离的数据目录。
无 Memory 组不配置 RepoMind MCP 服务器。

公开检查衡量常规仓库健康状况。外部隐藏检查在不向 Agent 暴露预期答案的情况下
衡量所要求的行为。实验完整性和任务结果验收分别评估。

## 完整性观察

- 全部 24 个 Agent 进程均正常退出。
- 全部 12 次 RepoMind 运行都检索到至少一条 Memory。
- 全部 12 个 RepoMind Session 均已提交，没有 Session 保持打开。
- 没有运行产生意外的文件变更。
- 没有记录到运行器 stderr。
- 无 Memory 运行没有调用 RepoMind。

## 限制

- 固件由 RepoMind 作者设计，因此存在选择偏差。
- 该套件只有四个小型 JavaScript 任务。
- 本次运行仅覆盖一个模型、一个运行器版本和一个操作系统。
- `historical-command` 被特意设计为仓库中缺少必需信息；它直接测试预期的
  Memory 优势。
- Token 数来自 OpenCode 事件，未使用独立的 tokenizer 重新计算。
- 三次重复不足以得出有力的延迟结论。
- A/B 设计整体衡量 RepoMind，无法单独区分内部检索、Session 或存储机制的影响。

该结果证明 RepoMind 在此受控套件上具有收益。它不能证明 RepoMind 能改善
每个仓库、任务、模型或运行环境。
