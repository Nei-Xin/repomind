结果验收门槛。

## 方法

该套件包含八个任务、三次重复和三个实验组，共 72 次 Agent 运行。每次运行都从
所记录任务 commit 的全新克隆开始。无 Memory 组不接收历史上下文；完整历史组
接收原始任务历史；RepoMind 组在 Agent 执行前接收检索到且有 Evidence 支持的
Memory。拉丁方调度会在各次重复之间轮换实验组顺序。

在宿主管理模式中，运行器会在 OpenCode 启动前启动 RepoMind Session、检索
Memory，并将该上下文注入任务 Prompt。Agent 循环内不会暴露 RepoMind MCP 工具。
OpenCode 退出后，宿主提取最终响应和命令 Evidence，并提交 Session。外部公开检查
和隐藏检查在提交后运行，其结果不会写回 Memory。

每次 RepoMind 运行都使用隔离的数据目录。OpenCode 以 `--pure` 运行，防止全局
插件添加工具、MCP 服务器或 Prompt 行为。隐藏验证器保留在任务仓库之外。
实验完整性和结果验收分别评估，全部阈值均在运行前固定在清单中。

## 完整性审计

- 预期的 72 个 JSONL 文件、stderr 文件、运行目录和隔离数据目录全部存在。
- 所有 stderr 文件均为空；没有计划运行缺失、重复或多余。
- 每个 Agent 进程都正常退出，所有公开检查均通过。
- 每次运行都使用要求的基线 commit，并且只产生允许的文件变更。
- 两个基线组均未使用 RepoMind。
- 每次 RepoMind 运行都检索 Memory 并提交 Session；未向 Agent 暴露 RepoMind
  MCP 调用，也没有 Session 保持打开。
- 离线分析重建并核对了全部 72 条时间线，没有完整性失败。

## 与 v0.7 结果的关系

保留的 v0.7 Agent 管理结果通过了实验完整性检查，但结果验收失败，因为 RepoMind
比完整历史慢 39.713%。新的宿主管理结果比完整历史快 12.711%，实测相对差值变化
52.424 个百分点。RepoMind 平均实际耗时从 v0.7 实验的 75.291 秒变为本次的
39.023 秒。

这些值来自不同的实验执行和 OpenCode 版本，因此其直接差值用于诊断，不能视为
配对因果估计。v0.8 的正式结论基于上方报告内的 24 组配对。v0.7 的负面结果在
[`agent-benchmark-results-v0.7.md`](agent-benchmark-results-v0.7.md)
中保持不变。

## 限制

- RepoMind 作者设计了八个小型 JavaScript 固件，因此存在选择偏差，外部有效性有限。
- 实验仅覆盖一个模型别名、一个运行器版本、一个操作系统和一个日期。
- 原始完整历史很短，且直接注入。真实仓库的历史可能过大或噪声过多，无法如此提供，
  但本实验没有测量这一扩展临界点。
- 每个任务重复三次仍是小样本。报告区间使用配对差值的正态近似。
- OpenCode 事件中的 Token 数未使用独立 tokenizer 重新计算。
- 外部公开检查和隐藏检查有意在 Session Commit 后运行，因此其结果不会成为
  此协议中的 Memory Evidence。
- 宿主管理生命周期是可选择启用的模式；为了向后兼容，默认仍为 Agent 管理模式。
