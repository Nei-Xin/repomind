# RepoMind v0.7 三组受控 Agent 基准结果

本文记录 RepoMind v0.7.1 的正式 report-v4 运行。实验通过了全部完整性检查，
但未通过预先声明的结果验收标准。唯一失败的门槛是相对于完整历史组的平均实际
耗时回归：实测 39.713%，上限为 15%。

这是有效的负面验收结果，不得将其描述为成功的 v0.7 结果验收。

## 方法

该套件包含八个任务、三次重复和三个实验组，共 72 次 Agent 运行。每次运行都从
所记录任务 commit 的全新克隆开始。无 Memory 组不接收历史上下文，完整历史组
接收原始任务历史，RepoMind 组则通过隔离的 MCP 服务器检索一条有 Evidence
支持的 Memory。拉丁方调度会在各次重复之间轮换实验组顺序。

隐藏验证器保留在任务仓库之外。每次 RepoMind 运行都使用隔离的数据目录。
OpenCode 以 `--pure` 运行，防止全局插件添加工具、MCP 服务器或 Prompt 行为。
实验完整性与结果验收分别评估，验收阈值在运行前已固定在清单中。

## 完整性审计

- 预期的 72 个 JSONL 文件全部存在，没有缺失、重复或额外运行。
- 审计解析了 2,413 个事件，没有格式错误的 JSON、Agent 超时、Agent 错误
  或失败的工具调用。
- 全部 72 个 Agent 进程均正常退出，所有公开检查均通过。
- 每次运行都使用要求的基线 commit，并且只产生允许的文件变更。
- 全部 72 个 stderr 文件均为空。
- 未观察到全局插件、Skill、后台 Agent 或委派工具。
- 两个基线组均未调用 RepoMind。
- 全部 24 次 RepoMind 运行都恰好检索一条预置 Memory 并提交其 Session；
  没有 Session 保持打开或被 abandoned。

## 阶段诊断

离线阶段分析器重建了全部 72 条原始时间线，并将其轮次、Token 和工具总数与
report v4 对齐。分析完整性通过，没有失败项。

| 阶段 | MCP 直接耗时 | 工具轮次周期 | 后续周期 | 工具轮次输入/输出 | 后续输入/输出 |
| --- | ---: | ---: | ---: | ---: | ---: |
| Session Start | 0.284 s | 2.366 s | 5.234 s | 797 / 118 | 818 / 95 |
| Session Commit | 0.448 s | 8.400 s | 4.980 s | 1,105 / 285 | 1,185 / 77 |

每次 RepoMind 运行中，Session Start 和 Commit 在 MCP 工具本身的直接耗时仅为
0.731 秒，约占其相对于完整历史 21.401 秒配对实际耗时差距的 3.4%。该配对差距
可拆分为可观察 Agent 事件流内部的 20.297 秒，以及进程启动或关闭的 1.104 秒
开销。因此瓶颈不在 SQLite 或 MCP 执行。

每次配对运行中，RepoMind 比完整历史多使用 2.833 个模型轮次、2.708 次工具调用、
4,562 个输入 Token、496 个输出 Token 和 25,067 个缓存读取 Token。强制的
Start 和 Commit 工具轮次及其后续轮次平均携带 3,905 个输入 Token 和 577 个
输出 Token。由于基线也需要普通工作和最终响应轮次，这些窗口用于诊断，
不能视为可相加的因果估计。

Commit 是更大的优化目标：其工具轮次和后续轮次共持续 13.380 秒，而 Start
周边为 7.600 秒；Commit 工具轮次生成的输出 Token 超过 Start 的两倍。
这与 Agent 构造详细 Commit 载荷，并在得到结果后再执行一个模型轮次的行为一致。

## 结果解读

与没有历史上下文相比，RepoMind 带来了明确的质量收益。在该套件上，它没有比
完整历史带来质量改善，并且额外的 Agent 轮次和 Token 产生了实质成本。完整历史组
均值为 53.890 秒，因此配置的 15% 上限最多允许 61.974 秒。在其他条件可比的
运行中，RepoMind 需要将当前均值降低约 13.318 秒才能满足该门槛。

## 下一步验收工作

下一轮应首先减少 Commit 载荷生成和 Commit 后的额外模型轮次，再减少 Start
结果上下文和重复的上下文重放。仅优化数据库无法弥合实测差距。在完成确定性测试
和一次单次重复的工程预检后，应在新输出目录中使用不变的清单和验收阈值重新运行。
替代运行必须与本结果并列报告，不能用它替换本结果。

## 限制

- RepoMind 作者设计了全部八个小型 JavaScript 固件，因此存在选择偏差，
  外部有效性也有限。
- 实验仅覆盖一个模型别名、一个运行器版本、一个操作系统和一个日期。
- 原始完整历史很短，且直接注入。真实仓库的历史可能过大或噪声过多，无法如此提供，
  但本实验没有测量这一扩展临界点。
- 每个任务重复三次仍是小样本。报告区间使用配对差值的正态近似。
- OpenCode 事件中的 Token 数未使用独立 tokenizer 重新计算。
- 该结果把 RepoMind 作为端到端 Agent 协议进行评估，无法区分存储、检索、MCP、
  Prompt 或 Session Commit 的各自成本。
