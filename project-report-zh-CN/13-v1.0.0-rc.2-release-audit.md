## 1. 发布结论

RC.2 已完成发布前工程审计、跨平台 CI、不可变 annotated tag、GitHub prerelease 和制品校验。该版本重点解决安装与首次使用，而不是增加新的 Memory 算法：有仓库访问权限的用户可以直接安装 Release `.tgz`，用 `repomind --version` 验证版本，通过 `init -> doctor -> run` 完成第一次 Host-managed Agent 任务。当前仓库为私有仓库，Release 不是匿名公共下载源。

GitHub Release：

```text

```

## 2. 为什么 RC.2 必须修安装流程

RC.1 已有完整 Core、CLI、MCP 和 Host 能力，但首次使用仍偏向源码开发者：README 主要描述 `npm link`，缺少可安装制品路径；`--version` 会被 CLI 参数解析拒绝；`doctor` 不探测 Agent；缺少 Runner 时可能在 Session 生命周期开始后才失败。

RC.2 将这些问题作为发布阻断项处理：

| 问题 | RC.2 修复 | 用户效果 |
| --- | --- | --- |
| 无清晰安装入口 | GitHub Release 发布版本化 `.tgz` | 不需要 clone/build 即可安装 |
| `--version` 报参数错误和 Node stack | 新增轻量 `dist/cli/entry.js`，支持 `--version`/`-v` | 可直接确认安装版本 |
| CLI 非法参数暴露 stack | 输出简洁 `INVALID_INPUT` 和 help 提示 | 首次使用错误可理解 |
| `doctor` 不检查 Agent | 支持 OpenCode/Claude 单个或全部 probe | 运行任务前发现环境问题 |
| Runner 缺失后才打开 Session | Host 在 Session Start 前做 executable preflight | 不留下无意义 open Session |
| 发布包包含 benchmark/隐藏 fixture | 收紧 npm `files` allowlist | 运行包从 337 个文件降至 236 个 |
| 没有自动发布路径 | tag-triggered Release workflow | 自动生成 `.tgz` 和 `SHA256SUMS` |

## 3. 安装和第一次使用

```powershell
npm.cmd install --global https://github.com/Nei-Xin/repomind/releases/download/v1.0.0-rc.2/repomind-1.0.0-rc.2.tgz
repomind --version

Set-Location D:\path\to\git-repository
repomind init
repomind doctor --runner opencode
repomind run --task "修复一个真实问题并运行相关测试" --runner opencode
```

使用 Claude Code 时将 `--runner opencode` 改为 `--runner claude`。Agent 不在 `PATH` 时使用 `--runner-executable <path>`。

公开 npm 上的无作用域 `repomind@1.4.0` 属于 `repomind-dev/repomind` 和其他维护者，因此不得使用：

```powershell
npm.cmd install --global repomind
```

当前正确分发边界是项目 GitHub Release。未来如果需要 npm registry，应先配置项目自有 scope，而不是占用或覆盖他人的包名。

## 6. 跨平台 CI 与发布过程

- repository/cross-session 测试比较非 canonical path；
- comparison fixture 仍允许 partial Session 产生 L1，与当前门禁冲突。

修复后提交 `dfe022f` 的 main CI run `31517673578` 在 10m29s 内通过五项门禁：

```text

### 6.2 tag CI

只有 main CI 通过后才创建并推送 annotated tag `v1.0.0-rc.2`。tag CI run `31518716468` 的第一次 Windows attempt 出现 Vitest worker RPC `onTaskUpdate` timeout：46/46 test files 和 266/266 assertions 实际全部通过，但两个未处理的 worker 汇报超时使进程返回 1。

同一不可变提交只重跑失败的 Windows job，attempt #2 在 8m34s 内成功；Ubuntu、macOS、coverage 和 bench 保持通过。该事件应解释为 Windows CI 稳定性技术债，而不是产品断言失败，但后续版本应降低对人工重跑的依赖。

### 6.3 Release workflow

Release run `31518716442` 在 3m05s 内成功，独立执行 typecheck、build、回归、fixtures 和 package smoke，再创建 GitHub prerelease 并上传：

```

## 7. RC.2 能证明什么

RC.2 发布证据能证明：

- 安装制品与源码版本一致；
- 版本、help、非法参数、初始化、doctor 和 Agent preflight 可用；
- CLI/MCP、加密恢复和 24 项 MCP Tool 能从安装包运行；
- tarball 不包含 benchmark、隐藏 fixture、数据库、测试或 coverage；
- Ubuntu、Windows、macOS 构建与回归门禁通过；
- GitHub prerelease 附件和 SHA-256 已核验。

它不能新增证明：

- L2/L3 对所有任务、仓库和模型都有普遍 uplift；
- Claude -> OpenCode 反向路径已经完成同类正式 repeat 5；
- Codex Host Adapter 已实现；
- 跨机器、多用户或云同步已经实现；
- live SQLite 数据库已经加密。

## 8. 发布后的正确工作重心

当前项目应进入 RC 稳定使用阶段，而不是继续堆叠重复实验：

1. 用 Release tarball 在至少两个真实仓库完成持续任务；
2. 观察首次安装耗时、Session/Host Run 是否闭合、错误 Memory 和恢复问题；
3. RC 期间只修 correctness、data safety、security、installation 和 compatibility 阻断项；
4. Windows Vitest worker RPC timeout 纳入 CI 稳定性改进；
5. 多任务、反向跨 Agent 或四臂消融只在产品决策需要时执行。
